大模型推理服务端到端健康检测设计

面向 Kubernetes 部署的 vLLM/OpenAI-compatible 推理服务，设计一套跨模型、跨版本、 可用于单实例摘流与全链路告警的真实推理探测方案。

目标与边界 总体架构 内部 Sidecar 探测 外部 Blackbox 探测 多模型适配 ConfigMap 设计 qwen3 YAML 改造示例 inference-prober:v1 实现 落地计划

1. 目标与边界

目标是在模型服务进程仍然存活、基础健康检查仍然返回成功的情况下，识别真实推理链路是否不可用。 典型故障包括 GPU/NPU 卡异常、vLLM engine 卡死、decode 异常、Istio 路由异常、网关异常、 HTTP 200 但响应结构异常等。

核心原则：探测组件不依赖 vLLM 内部 Python API，不绑定具体 vLLM 版本， 只通过 HTTP 请求 OpenAI-compatible 推理接口完成验证。

设计边界

  • 不改模型业务接口协议。
  • 不把探测逻辑写进每个 vLLM 镜像。
  • 探测请求必须低成本，避免明显影响线上 P99 和 GPU batch。
  • 探测结果可用于 K8s 摘流、Prometheus 告警和平台巡检。

3. 内部 Sidecar 探测设计

Sidecar Prober 跟随模型 Pod 部署，定时请求本地 vLLM 接口，例如 http://127.0.0.1:8000/v1/chat/completions。 它将探测结果缓存到内存，并通过自己的 /readyz 暴露给 K8s。

工作流程

  1. 后台线程按固定间隔发起真实推理请求。
  2. 校验 HTTP 状态码、JSON 结构、接口类型对应字段和延迟。
  3. 连续失败达到阈值后，将本地状态标记为 unhealthy。
  4. K8s readinessProbe 访问 sidecar 的 /readyz。
  5. /readyz 返回 503 后，该 Pod 从 Service endpoints 摘除。
  6. 连续成功达到阈值后，/readyz 恢复 200，Pod 重新接流量。
注意：/readyz 不实时触发推理，只返回后台探测缓存结果。 否则 kubelet 的高频 probe 会直接消耗 GPU/NPU 推理资源。

推荐参数

参数 建议值 说明
INTERVAL_SECONDS 30 后台真实推理探测间隔。
TIMEOUT_SECONDS 5 单次探测超时时间。
FAILURE_THRESHOLD 3 连续失败多少次后摘流。
SUCCESS_THRESHOLD 2 连续成功多少次后恢复。
LATENCY_THRESHOLD_MS 5000 超过阈值视为探测失败。

4. 外部 Blackbox 探测设计

Blackbox Prober 独立部署，不在模型 Pod 内。它从业务入口或网关域名发起请求， 用来覆盖 Gateway、Istio、VirtualService、Service、Pod 到 vLLM 的端到端链路。

适用场景

  • 业务域名不可访问。
  • Istio VirtualService rewrite 或 header 路由异常。
  • 网关超时、连接池、鉴权配置异常。
  • 服务整体 SLA 告警。
  • 多模型、多集群巡检。

Blackbox target 示例

apiVersion: v1
kind: ConfigMap
metadata:
  name: model-blackbox-prober-targets
  namespace: prod-pre
data:
  targets.yaml: |
    targets:
      - name: qwen3-32b-fp8-v2
        type: chat
        url: http://pre-llm-inference-api.brapp.com/qwen3-32b-fp8/v1/chat/completions
        model: qwen3-32b-fp8
        intervalSeconds: 30
        timeoutSeconds: 5
        latencyThresholdMs: 5000
        failureThreshold: 3
        successThreshold: 2
        headers:
          content-type: application/json
        body:
          messages:
            - role: user
              content: ping
          max_tokens: 1
          temperature: 0

5. 多模型与多接口适配

Prober 通过 PROBE_TYPE 或 target 的 type 决定请求和校验方式。 这样同一套镜像可以覆盖 chat、completion、embedding、rerank 等模型。

类型 接口 最小请求 成功校验
chat /v1/chat/completions messages + max_tokens=1 choices[0].message.content 或 tool_calls 存在，usage.total_tokens > 0
completion /v1/completions prompt + max_tokens=1 choices[0].text 存在。
embedding /v1/embeddings input=ping data[0].embedding 是非空数组。
rerank /v1/rerank 或 /rerank query + documents results、scores 或 data 存在。

6. ConfigMap 设计

ConfigMap 用来保存探测目标和请求体，让 prober 镜像保持通用。Sidecar 与 Blackbox 的配置粒度不同。

Sidecar 配置

Sidecar 只探测当前 Pod 内的一个模型，第一版可以直接用环境变量配置。模型数量多起来后， 可以改成每个模型一个独立 ConfigMap。 

apiVersion: v1
kind: ConfigMap
metadata:
  name: qwen3-32b-fp8-v2-prober-cm
  namespace: prod-pre
data:
  probe.yaml: |
    name: qwen3-32b-fp8-v2
    type: chat
    url: http://127.0.0.1:8000/v1/chat/completions
    model: qwen3-32b-fp8
    intervalSeconds: 30
    timeoutSeconds: 5
    failureThreshold: 3
    successThreshold: 2
    body:
      messages:
        - role: user
          content: ping
      max_tokens: 1
      temperature: 0

Blackbox 配置

Blackbox Prober 负责巡检多个模型入口，适合用一个集中 ConfigMap 管理所有 target， 也可以按 namespace、业务线或环境拆分。

7. qwen3-32b-fp8-v2 YAML 改造示例

在你的 Deployment 中保留原 vLLM 容器，并新增 inference-prober sidecar。

containers:
  - name: app
    image: registry.100credit.cn/xdynamic/x86_64/nvidia/vllm-openai:v0.10.2
    command:
      - /bin/sh
      - -c
      - |
        vllm serve /MODEL \
          --chat_template /MODEL/chat_template.jinja \
          --trust-remote-code \
          --quantization compressed-tensors \
          --enable-chunked-prefill \
          --enable-prefix-caching \
          --dtype auto \
          --max-model-len 20480 \
          --max-num-batched-tokens 8192 \
          -tp 2 \
          --served-model-name qwen3-32b-fp8 \
          --gpu-memory-utilization 0.9 \
          --enable-auto-tool-choice \
          --tool-call-parser hermes
    ports:
      - containerPort: 8000
        name: http
        protocol: TCP
    readinessProbe:
      httpGet:
        path: /health
        port: 8000
      initialDelaySeconds: 3
      periodSeconds: 10

  - name: inference-prober
    image: registry.100credit.cn/xdynamic/llmops/inference-prober:v1
    imagePullPolicy: IfNotPresent
    env:
      - name: PROBE_NAME
        value: qwen3-32b-fp8-v2
      - name: PROBE_TYPE
        value: chat
      - name: TARGET_URL
        value: http://127.0.0.1:8000/v1/chat/completions
      - name: MODEL_NAME
        value: qwen3-32b-fp8
      - name: INTERVAL_SECONDS
        value: "30"
      - name: TIMEOUT_SECONDS
        value: "5"
      - name: FAILURE_THRESHOLD
        value: "3"
      - name: SUCCESS_THRESHOLD
        value: "2"
      - name: LATENCY_THRESHOLD_MS
        value: "5000"
      - name: PROBE_BODY
        value: |
          {
            "model": "qwen3-32b-fp8",
            "messages": [
              {
                "role": "user",
                "content": "ping"
              }
            ],
            "max_tokens": 1,
            "temperature": 0
          }
    ports:
      - containerPort: 18080
        name: probe
        protocol: TCP
    readinessProbe:
      httpGet:
        path: /readyz
        port: 18080
      initialDelaySeconds: 60
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 1
    resources:
      requests:
        cpu: 100m
        memory: 128Mi
      limits:
        cpu: 500m
        memory: 512Mi
K8s 只有当 Pod 内所有容器都 Ready 时，Pod 才会进入 Service endpoints。 因此 sidecar 的 /readyz 失败后，这个模型 Pod 会自动被摘流。

8. inference-prober:v1 实现建议

第一版可以用 Python 实现，镜像只依赖 requests，保持轻量。

接口

路径 用途 返回
/livez prober 进程存活。 固定 200。
/readyz 返回后台探测缓存结果。 healthy 返回 200，unhealthy 返回 503。
/metrics Prometheus 指标。 probe 成功状态、延迟、连续失败次数等。

核心指标

inference_probe_ready{model="qwen3-32b-fp8",type="chat"} 1
inference_probe_latency_ms{model="qwen3-32b-fp8",type="chat"} 42
inference_probe_consecutive_failures{model="qwen3-32b-fp8",type="chat"} 0
inference_probe_last_success_timestamp{model="qwen3-32b-fp8",type="chat"} 1781493603

错误分类

  • timeout：请求超时。
  • connection_error：连接失败。
  • http_5xx：服务端错误。
  • http_4xx：请求或鉴权异常。
  • json_parse_error：响应不是合法 JSON。
  • schema_invalid：响应结构不符合对应模型类型。
  • empty_output：响应为空。
  • latency_exceeded：延迟超过阈值。

9. 落地计划

第一阶段：单模型 Sidecar 灰度

  • 实现 inference-prober:v1。
  • 接入一个 chat 模型，例如 qwen3-32b-fp8-v2。
  • 观察探测 QPS、latency、业务 P99 是否受影响。
  • 验证连续失败后 Pod 是否自动摘流。

第二阶段：多模型适配

  • 增加 embedding、rerank、completion 校验逻辑。
  • 抽象 probe profile，让平台根据模型类型自动生成配置。
  • 为不同模型设置不同 interval、timeout 和 latency 阈值。

第三阶段：外部 Blackbox 巡检

  • 部署独立 blackbox prober。
  • 通过 ConfigMap 管理所有模型入口。
  • 接入 Prometheus 和 Alertmanager。
  • 按模型、namespace、业务域名、集群维度配置告警。

最终形态

单 Pod 故障摘流：Sidecar Inference Prober
端到端链路告警：Blackbox Inference Prober
多模型适配：probe_type + request body + validation rule
跨版本适配：只依赖 OpenAI-compatible HTTP API
